# KnowPilot V2.0.0 发布检查清单及实施 Plan

**状态：待审。** 负责人为项目协调者。开发验收依据为 [Issue #13](https://github.com/IUBOBO/KnowPilot/issues/13)、[G5 报告](gates/G5.md) 和 [PR #39 的实际合并提交](https://github.com/IUBOBO/KnowPilot/commit/2510e1b3ee2d80492dad5bc8d48a9c80f3b7a10d)。发布候选 SHA 在发布文档经审查合并后确定。

## 范围与交付物

以 G5 已验收的功能为基线，整理使用、部署和运维说明，编写版本说明，并在批准后将 GitHub Release 与 `v2.0.0` 标签绑定到同一候选提交。范围限文档和 GitHub 版本发布。业务代码、数据库迁移和依赖不随本 Plan 变更。现有公开资料优先修订或引用。本阶段只提交清单与 Plan。

仓库已有 `README.md`、通过验收的 G0–G5 报告、路线图和 [证据回调契约](contracts/EVIDENCE-OPEN.md)。前端生产构建可由 Hono 在 `SERVE_WEB=1` 时托管，服务另有独立迁移命令。当前仓库的 npm 工作区为私有，package 及 `SERVICE_VERSION` 为 `0.1.0`。本 Plan 建议用 Git 标签和 GitHub Release 标识产品版本，在发布说明中注明内部版本字段。统一版本字段需另行批准。

## 实施 Plan

| 顺序 | 实施范围 | 验收证据与停止点 |
|---|---|---|
| 1. 审查与冻结候选 | 用户审查本 Plan 后，从最新已验收的 `main` 建立发布文档分支。核对既有文档、PR #39 和候选业务差异。 | 记录起点 SHA、允许变更范围及 G5 证据索引。出现功能差异先定位来源并确认范围。 |
| 2. 整理文档 | 复用 `README.md`。优先将系统与 Agent 架构合入一份公开架构文档，将配置并入部署文档，将数据库与备份恢复并入运维文档。发布说明在文档 PR 中预览。 | 预期路径为 `README.md`、`docs/architecture.md`、`docs/deployment.md` 和 `docs/operations.md`，开工时以最新主分支现有同类文档为准。公开内容只引用可发布材料。 |
| 3. 验证关键操作 | 用独立工作树、临时 `DB_PATH`、`UPLOAD_DIR`、回环端口和合成资料执行 `npm ci`、`npm run typecheck`、`npm run build -w @knowpilot/web`、隔离库 `npm run migrate` 和 `npm run start -w @knowpilot/server`，核对 `/health` 与认证。用 v37 测试副本验证备份、恢复及 v38 迁移，并记录完整性和关键数据保留。 | 保存环境、命令、退出码和证据索引。选用 `npm run verify-auth -w @knowpilot/server` 定向检查。出现新增失败或数据不一致先修正复验。真实模型及 BGE-M3 实机评测沿用 G5 记录，如需复测须另获授权。 |
| 4. 文档与发布前审查 | 提交发布文档 PR，核对公布文本、命令、已知问题、敏感内容和预期源码归档。获批合并后再次核对实际候选 SHA 与 tree。 | 提交可复核的发布清单和候选证据。候选、附件及版本说明全部经人工批准后才执行标签和 Release。 |
| 5. 发布与核验 | 将 `v2.0.0` 指向批准的候选 SHA，复核 GitHub Release 草稿后发布。记录标签对象、解析出的提交 SHA、Release URL 和发布说明。 | 核对下载归档与标签一致。发现异常暂停分发和部署。已有标签保留原指向，发布更正使用可追溯的修订。 |

部署与恢复演练使用隔离环境。实际升级需在维护窗口按独立授权执行。若需回退，先停止写入并保全故障状态，用迁移前的完整数据快照在新目录演练恢复，核对原件、索引和数据库对应关系后再切换。旧二进制与已升级库的兼容性须单独确认。
